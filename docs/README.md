# Документация проекта

> Статус: **active**. Индекс документов. Обязательный краткий контракт — в
> `AGENTS.md`, подробные правила — в самих документах.

## Порядок чтения

1. `AGENTS.md` — команды, инварианты и карта «что читать под задачу».
2. Этот файл — выбрать актуальный документ по теме.
3. Соответствующий план или checklist темы.
4. Исходники, конфигурация и тесты рядом с изменяемым кодом.

## Правила

- У каждой темы ровно один владелец: остальные документы ссылаются на него, а не
  пересказывают. Новый документ создаётся, только если темы нет в существующем.
- У документа есть статус (`draft`, `active`, `completed`) и понятная область
  применения. Ссылки на конкретный файл или команду проверяются при изменении
  источника истины.
- Подробные материалы живут в `docs/`, а не в корне. Не создавать отдельные
  `docs/commands.md` или `docs/known-issues.md`: команды принадлежат
  `quality-gates`, известные проблемы — XBOCT-Log и checklist. `README.md` в
  корне остаётся кратким обзором продукта, а не вторым руководством агента.
- **Задачи живут в XBOCT-Log** (проект `eit`, `EIT-*`). Документ описывает
  решения и правила, а не учёт работ; ссылка на задачу — по её id, обратная
  синхронизация не ведётся.
- Выполненные пункты из документов удаляются: история остаётся в git. Отдельного
  архива нет — если понадобится старый текст, он берётся из git history.
- Ссылаясь на инструмент, сверяться с реестром: внутреннее имя (`id`) — в
  `web/src/lib/registry/tools/`, адрес и имя страницы (`slug`) — в
  `web/src/lib/registry/pages/`; исторические названия в старых планах не
  действуют (`docs/architecture.md`, раздел 3).
- Поиск по `docs/*.md` — актуальный корпус документации.
- Проверка ссылок в документации не автоматизирована; любая неразрешимая ссылка
  — ошибка.
- Протокол «остановиться и показать изменения» — `docs/agent-workflow.md`,
  раздел 6.
