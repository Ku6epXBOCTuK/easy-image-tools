# Roadmap: направления развития

> **Статус: active.** Документ фиксирует **решения и порядок фаз**, а не учёт
> работ: открытые задачи живут в XBOCT-Log (проект `eit`, задачи `EIT-*`), здесь
> только то, что определяет архитектуру и очередь.
>
> **Метки:** `done` — сделано и покрыто тестами; `partial` — часть в коде, часть
> в задачах; `not started` — кода нет.

## 0. Решения

- **Всё считается в браузере.** Загруженный файл не покидает устройство; ядро
  работает над `ImageData`, без DOM и без сети. Это продуктовое обещание и
  техническое ограничение одновременно.
- **TS-ядро — эталон поведения.** Пока Rust-версия не совпала с TS на эталонах,
  права считаться правильной у неё нет. Обратное неверно: TS можно менять, но
  каждое изменение фиксируется эталоном.
- **Пайплайн — данные, а не код.** Шаг описывается `{ id, params }`; цепочка —
  массив шагов. Один и тот же формат используют UI, localStorage, будущие
  CLI/API и экспорт JSON.
- **Два класса результата.** `bit-exact` — пиксели обязаны совпасть с эталоном
  (целочисленные операции, палитры, геометрия без ресемплинга). `perceptual` —
  допускается расхождение от хинтинга, антиалиасинга и разных декодеров (текст,
  ресемплинг, фильтры). Правила сравнения — §3.
- **Одно ядро — несколько рантаймов.** Rust-ядро собирается в wasm для сайта,
  нативный бинарник для CLI и нативный сервис для API. API — **нативный Rust**,
  а не wasm: память и время на больших файлах, отсутствие накладных расходов
  рантайма. Edge-воркеры — исключение для дешёвых операций, не основной путь.
- **PWA не меняет SEO-схему.** Страницы остаются prerendered и одинаковыми для
  ботов; service worker не перехватывает навигацию ботов и не подменяет HTML.
- **API обрабатывает файлы в памяти.** Без постоянного хранилища изображений:
  запрос → обработка → ответ, файл не пишется на диск и не логируется.
- **Монетизация не ломает «no upload».** Платные тиры API/PWA не меняют
  браузерный сценарий: он остаётся бесплатным и локальным.

## 1. Фазы

### Фаза 1 — TS-ядро и UI (done)

Типизированный реестр инструментов и страниц, операции над `ImageData`, i18n,
темы, загрузка/скачивание, схема параметров. Точки расширения —
`docs/architecture.md` §3–4.

### Фаза 2 — эталонные фикстуры (partial)

Есть краевые входы `tests/fixtures/manual-edge-cases/` (генератор
`pnpm generate:fixtures`). Нет `tests/reference/<op>/input-*.png` +
`expected-*.png`: без них `harness compare` нечего сравнивать.

### Фаза 3 — регресс UI (partial)

E2E-набор покрывает каталог, потоки инструментов и smoke; ручная приёмка —
`docs/checklist-manual-testing.md`. Нет генератора эталонов и регресса по
`expected-*.png`; визуальные снимки осознанно заменены чек-листом
(`docs/decisions.md`).

### Фаза 4 — Rust-ядро (not started)

Порт операций из TS в `core/` (Rust): те же входы/выходы, чистые функции без
DOM. Критерий готовности фазы — паритет на эталонах фазы 2, а не количество
портированных операций.

### Фаза 5 — wasm (not started)

Сборка ядра в wasm и замена реализации **внутри** исполнителя
(`web/src/lib/executor/`), без правок компонентов. TS остаётся фолбэком для A/B
и для окружений без wasm.

### Фаза 6 — CLI и harness compare (not started)

CLI над нативным ядром и `harness compare` — прогон эталонов с отчётом
`bit-exact`/`perceptual`. Это же гейт паритета для фаз 4–5.

### Фаза 7 — паритет и пайплайн в CLI (not started)

Все шаги пайплайна исполняются в CLI так же, как в браузере; расхождения
классифицируются по §3. Только после этого имеет смысл API: контракт не должен
меняться из-за недоделанного ядра.

### Фаза 8 — batch и тяжёлое сжатие (not started)

Пакетная обработка файлов/архивов, прогресс и отмена, `oxipng`/`zopfli` для
оптимизации без потерь. В браузере остаётся TS-сжатие (`fitWithinBytes`), batch
— первый сценарий, где нативное ядро даёт заметную выгоду.

### Фаза 9 — API (not started)

1. **Спайк:** нативный Rust на VPS против wasm на edge — стоимость, лимиты
   памяти/времени на больших картинках, сложность деплоя и rate-limiting.
2. **Контракт:** `POST /v1/process` — multipart (image) + JSON-пайплайн →
   изображение/архив; лимиты размера, коды ошибок, OpenAPI.
3. **Ключи и лимиты:** Bearer-ключи, free tier, rate limiting по ключу.
4. **Биллинг:** 2–3 тира по запросам/размеру, только после стабильного free
   tier.
5. **Документация:** `/api` как лендинг — туториал, примеры curl/JS, OpenAPI.

Условие старта: закрыта фаза 7. Файлы обрабатываются в памяти (§0).

### Фаза 10 — PWA (not started)

1. **Манифест:** имя бренда, иконки 192/512 + maskable, `theme-color` из
   токенов, `display: standalone`.
2. **Service worker:** precache app-shell; ассеты с build-hash — cache-first;
   навигация — stale-while-revalidate; offline-fallback. Вес precache оценить
   спайком.
3. **Оффлайн-UX:** индикатор «offline — работаете локально», кнопка установки на
   `beforeinstallprompt`, стратегия обновления версии.
4. **SEO-безопасность:** SW не перехватывает ботов, не меняет HTML; canonical и
   prerendered-страницы не затрагиваются. Проверка — Lighthouse PWA + SEO.

Условие старта: SEO-слой стабилен (`docs/plan-seo.md`); PWA — дистрибуция, а не
новый контент.

### Фаза 11 — пайплайн (partial)

**Есть:** `pipeline.svelte.ts`, `chains.svelte.ts`, маршруты `/pipeline` и
`/chains`, исполнение всей цепочки (`run-chain.ts`), drag-n-drop шагов
(`step-dnd.svelte.ts`), маски шагов (`step-mask.svelte.ts`), именованные цепочки
в localStorage, fan-out, zip.

**Нет:** UI экспорта/импорта JSON (есть только `parseChain`/`serializeSteps`;
ключи `errors.badPipelineShape`, `pipelineVersion`, `noSteps` в словарях не
используются). Остальное — задачи `EIT-*` (batch-архивы, прогресс/отмена,
parts-grid).

**Ограничения, которые нельзя терять при доработке:** цепочка — 1→many и many→1;
частичные ошибки не отменяют всю цепочку; имена частей предсказуемы; порядок
шагов восстанавливается из JSON без потери параметров.

### Шрифты (перед фазой 8)

Нужны для переноса text-инструментов в ядро: в браузере canvas-рендер остаётся
TS-фолбэком, в Rust нужен рендер без DOM.

- **Лицензии:** только SIL OFL 1.1 и Apache 2.0 — коммерческое использование и
  встраивание в сайт, PWA, CLI, API. Запрещены «free for personal use»,
  shareware, шрифты без явной лицензии, MS core fonts. Проверять право класть
  TTF в дистрибутив, а не только веб-использование.
- **Паспорт шрифта:** `core/fonts/<name>/` — файлы, LICENSE, источник, версия,
  хеш. Новый гейт «у каждого файла шрифта есть паспорт» добавляется в
  `pnpm verify` по правилам `docs/quality-gates.md`.
- **Источник:** бандл (Fontsource/Google Fonts), не `fonts.googleapis.com`-CDN:
  сторонний запрос — утечка IP и зависимость от чужой инфраструктуры.
- **Кириллица:** приоритет семействам с полным покрытием. Судьбу IBM Plex
  (сейчас в бандле) решить при введении паспорта.
- **Рендер без DOM:** спайк `ab_glyph`/`rusttype` + `swash`/`harfrust` →
  отрисовка в `Image`. Эталон — canvas-рендер TS, класс `perceptual`: совпадать
  обязаны позиция, выравнивание, переносы; пиксели будут отличаться.
- **Единый текстовый API:** шрифт — `id` из реестра, а не системное имя; метрики
  базовой линии считать в ядре, а не через canvas `measureText`, иначе TS и Rust
  разъедутся.

## 2. Правила сравнения

| Класс        | Что проверяем                                              | Допуск                          |
| ------------ | ---------------------------------------------------------- | ------------------------------- |
| `bit-exact`  | целочисленные операции, палитры, геометрия без ресемплинга | пиксель в пиксель               |
| `perceptual` | текст, ресемплинг, фильтры, сжатие                         | визуально идентично, метрика §3 |

Для `perceptual` сравниваем не «на глаз»: размер, альфа-канал и средняя разница
по каналам с порогом, зафиксированным в harness. Порог меняется только вместе с
эталоном и обоснованием в задаче.

## 3. Риски

- **Canvas не бит-в-бит между браузерами.** Разные реализации сглаживания и
  цветовых пространств; поэтому `bit-exact` ограничен операциями без ресемплинга
  и интерполяции.
- **Разные декодеры PNG.** Цветовой профиль, 16-бит, interlaced — вход может
  декодироваться по-разному. Эталоны фиксируют конкретный декодер.
- **Расхождение TS и Rust накапливается.** Без `harness compare` в CI паритет
  деградирует молча; гейт обязателен до появления API.
- **Шрифты — юридический риск, а не технический.** Ошибка в лицензии всплывает
  после релиза; паспорт и белый список закрывают это до добавления файла.
- **PWA и кеш.** Устаревший service worker может отдавать старый HTML дольше,
  чем нужно; стратегия обновления проектируется вместе с PWA, а не после.

## 4. Проверки

До появления Rust-ядра и harness единственный автоматический гейт —
`pnpm verify`; e2e — по правилам `docs/quality-gates.md`, статус читается по
отдельному job в CI (`docs/decisions.md`, раздел 10). `cargo test` и
`harness compare` появятся вместе с фазой 6 — до этого ссылаться на них нельзя.
